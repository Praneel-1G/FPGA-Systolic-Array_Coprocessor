Yes! Exactly.

Because that block starts with the word forever, it acts like a security camera that never turns off.

Here is why it "runs every time" and how that works in the simulation:

1. It is a "Background Thread"

In Verilog, every initial block starts at Time = 0 and runs at the same time as every other block.

Block A (The Master Script): This is busy sending opcodes and pixels.

Block B (The Receiver): This is just sitting there, staring at the tx wire, waiting for it to wiggle.

2. It is "Trigger-Based"

It doesn't just run randomly. Look at this specific line:
@(negedge tx);

This is the "Trigger." The code inside that forever loop "freezes" at this line. It uses zero processing power. It just waits.

As soon as the FPGA pulls the tx wire from High (1) to Low (0) to start a UART transmission, the trigger fires!

The code "wakes up," records the 8 bits of that specific byte, saves it into captured[cap_idx], increments the counter, and then immediately loops back to the top to wait for the next negedge tx.

3. It catches EVERY byte

Because it is in a forever loop, it will catch:

Result Byte 0...

Result Byte 1...

...all the way to Result Byte 15.

It doesn't care when they arrive. If the FPGA sends them back-to-back, it catches them. If the FPGA waits an hour between bytes, it still catches them.

4. Why this is better than a "regular" function:

If we put the "receiving" code inside the Master Script, the script would look like this:

Send Pixel 16.

Receive Result 0.

Receive Result 1.

The Danger: If the FPGA starts sending Result 0 while the script is still finishing the "Send Pixel 16" command, the script is "busy" and would miss the start of the message.

By having captured run "every time" in the background, it is impossible to miss data. It’s like having a voicemail service—even if you are busy talking to someone else, the receiver is always ready to record the incoming message.

Summary

Does it run every time? Yes, it is always "listening."

Does it run for every byte? Yes, the forever loop ensures it resets after every byte caught.

Is it automatic? Yes, it is triggered by the hardware signal (tx) itself, not by you calling a function.This table provides a cycle-by-cycle "X-Ray" of what is happening inside your FPGA during the high-speed math phase.

Detailed Breakdown of the Logic
1. Why the "Staircase" Capture?

Because you injected data row-by-row with a delay (Skewing), the results finish at different times.

Column 0 starts its math at Cycle 0 and finishes its 4th calculation at Cycle 9.

Column 3 doesn't even receive its first piece of data until Cycle 3, so it doesn't finish its 4th calculation until Cycle 12.

2. The Structural Transpose (Mapping Col to Row)

A Systolic Array naturally flips the matrix (Transposes it). Look at how the code maps the columns to the out_buffer:

At Cycle 7, flat_ppu_out[15:8] (Column 1) is saved into out_buffer[4].

In your grid, out_buffer[4] represents Row 1, Column 0.

This specific mapping ensures that even though the hardware calculated the matrix "sideways," the bytes are stored in the correct order for the Python script to read them as a normal image block.

3. The Latency Gap

Notice that Injection ends at Cycle 6, but Capture continues until Cycle 12. This 6-cycle "tail" is the time required for the very last pixel (buf[15]) to:

Enter the Row 3 door (Cycle 6).

Multiply by the weight.

Add the sum from the PE above it.

Travel through the PPU's ReLU/Clamping logic.

Get registered and finally appear at the Controller’s input.

4. Finish Line

At Cycle 13, the out_buffer is now a perfectly ordered 16-byte array. The FSM transitions to S_TX_RESULTS, and the TPU starts pushing those 16 bytes into the UART to be sent back to your screen.
